# Migration foundation

This is the bounded foundation for migrating «Дым над льдом». The existing root
instructions and [content-delivery contract](contracts/content-delivery/AGENTS.md)
remain authoritative. No production entity has been migrated and no authority
switch or application delivery has occurred.

Start with the [migration report](migration/README.md), then the applicable
[SOURCE filling rules](source/AGENTS.md) and
[controlled vocabulary](schemas/foundation.yaml). The seven initial types are
character, vehicle, material, event, group, chapter and slice. Scenes, stories,
versions, transitions and social accounts are reserved for later bounded work;
they are not silently collapsed into character cards or app keys.

## Physical layout

```text
AGENTS.md                         existing global invariants
source/AGENTS.md                  initial type authoring and temporal rules
source/<type>/<id>.md             future SOURCE cards; none migrated yet
assets/<material-id>/...          future source binaries, owned by material refs
schemas/foundation.yaml          initial type/key/relation vocabulary
contracts/content-delivery/      existing boundary contract + future lock format
migration/AGENTS.md              evidence/baseline update procedure
migration/baseline.yaml          exact revisions, inspected paths, open issues
tests/AGENTS.md                  TEST isolation and verification rules
tests/fixtures/migration-probe.yaml  small evidence-backed model probe
tools/foundation.py              bounded validator, query and derived TEST index
generated/                       ignored DERIVED index/probe output
```

Future cards are Markdown with YAML frontmatter, for example:

```yaml
---
id: char-sergey-akunin
type: character
name: Сергей Андреевич Акунин
---
```

Names, aliases and paths may change without changing this ID. Universal fields
stay minimal; type-specific fields live in the local specification. There is no
manual entity registry containing another copy of the card's facts.

## Run the bounded proof

Use Python 3.12+ with `pip install -r requirements.txt` in a virtual environment.

```text
python tools/foundation.py validate tests/fixtures/migration-probe.yaml
python -m unittest discover -s tests -v
python tools/foundation.py probe tests/fixtures/migration-probe.yaml --output generated/migration-probe.json
python tools/foundation.py probe tests/fixtures/migration-probe.yaml --opened-ref doc-sergey-confession --output generated/migration-probe-opened.json
```

Outputs are DERIVED, TEST-scoped and excluded from Git. Repeating an unchanged
probe leaves the output file untouched. The real probe deliberately includes
unknown material dates and a planned photograph with no binary; it exercises
semantics and reports limitations, not production package readiness. The CLI
accepts the TEST fixture wrapper, not an entire production SOURCE repository.
The complete diagnostic JSON is author-only: it includes the author index and
world history alongside nested player allowlist results. Never deliver this
combined diagnostic file to a player client.

## Entity index and future incremental work

The generated author index maps stable IDs to type, name, aliases, source
locator, content hash, outgoing references and incoming backlinks. It never
owns authored facts or enters the player package. In this probe a locator points
inside the TEST fixture; the production locator will be the Markdown path.
Alias/name lookup can have multiple matches; resolve them rather than merging
identities. Hash algorithm and scope must be explicit (Git blob SHA for pinned
evidence, SHA-256 for generated bytes/parsed entity content).

Future index header: SOURCE revision, schema version and generator revision.
Future update input: `git diff --name-status <processed-revision> <new-revision>`
plus hashes for changed binaries. Read changed governing rules first. Re-index
changed cards, preserve IDs on rename, remove deleted rows, and follow incoming
dependencies to affected events, assertions and slices. Referenced deletions
fail validation; they do not cascade-delete canon or reuse an ID. Stage results
and replace the index only on success. Never rewrite identical bytes.

The foundation fixture index is deliberately rebuilt from just 12 test entities;
there is no production incremental index implementation yet. Its API and the
baseline separate the future batch delta from a full content scan. A first SOURCE
inventory, a changed global schema, or a corrupt index can justify a bounded
rebuild under the existing instructions.

## Validation boundary

Executable checks cover this initial vocabulary: required/type fields, unique
IDs, typed links and assertion addresses, valid time precision and ordering,
state ownership, chapter/slice coordinates, availability and opened-state gates,
player output allowlisting, assets when a path/hash is supplied, deterministic
output and no-op writes. Tests include invalid and boundary cases.

Human checks still own canonical source priority, semantic duplicate facts,
truth of claims, causality, author decisions and spoiler review of free text.
Before a production batch, add Markdown card loading, provenance/baseline
integration, incremental dependency persistence, production asset checks and
projection schema validation. Before delivery, add the consumer and old-save
tests, package hashing and atomic publication described by the contract. None
of those unimplemented checks is claimed as passed by the fixture probe.
