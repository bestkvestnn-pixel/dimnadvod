# Синхронизация между dimnadvod и test-app

## Роли

`dimnadvod` — AUTHOR / CANON / KNOWLEDGE SOURCE.

`test-app` — PLAYER / RUNTIME APPLICATION.

Направление авторских данных:

> **dimnadvod → test-app**

Приложение может хранить сгенерированные копии данных, но не становится самостоятельным источником канона.

## Три класса данных

- **SOURCE** — авторские канонические данные в `dimnadvod`.
- **GENERATED** — производные данные приложения.
- **RUNTIME** — состояние конкретной партии.

Эти классы нельзя смешивать.

## Синхронизация по дельте

Синхронизация по умолчанию инкрементальная.

```text
ПОСЛЕДНИЙ УСПЕШНЫЙ BASELINE
        ↓
СРАВНЕНИЕ РЕВИЗИЙ
        ↓
СПИСОК ТОЛЬКО ИЗМЕНЁННЫХ ПУТЕЙ
        ↓
СНАЧАЛА ИЗМЕНЁННЫЕ ИНСТРУКЦИИ
        ↓
ИЗМЕНЁННЫЕ SOURCE-ФАЙЛЫ
        ↓
ТОЛЬКО НЕОБХОДИМЫЕ ЗАВИСИМОСТИ
        ↓
ТОЛЬКО ЗАТРОНУТЫЕ ЭКСПОРТЫ
        ↓
ВАЛИДАЦИЯ
        ↓
ПУБЛИКАЦИЯ
        ↓
MANIFEST ОБНОВЛЯЕТСЯ ПОСЛЕДНИМ
```

Полное чтение обоих репозиториев не является штатным режимом.

## Изменение инструкций

Если изменились:
- корневой или локальный `AGENTS.md`;
- шаблон;
- схема;
- словарь;
- exporter;
- validator;

сначала читается новое правило, затем данные под его областью.

Изменение текста правила не означает автоматическую массовую миграцию.

## Классы изменений

Каждый путь классифицируется как:
- added;
- modified;
- deleted;
- renamed/moved;
- instruction/schema changed;
- binary asset changed.

Определять это нужно через diff/compare, manifest, hashes или сохранённый baseline.

## Зависимости

После определения изменённых SOURCE-файлов читать только зависимости, необходимые для корректного экспорта.

Расширение области должно идти через:
- стабильные ID;
- индекс;
- manifest;
- явные export dependencies.

Не загружать все главы, персонажей и материалы без причины.

## Generated-граница

Generated-файлы:
- не редактируются как канон;
- заменяются регенерацией;
- должны быть отделены от кода и runtime;
- ручные изменения внутри них считаются drift, а не новой истиной.

## Что не синхронизируется обратно

В канон не переносятся автоматически:
- UI;
- CSS;
- компоненты;
- storage-механика;
- прогресс;
- ответы;
- настройки;
- debug/test данные.

Если приложению требуется новое поле, это предложение по изменению схемы, а не reverse sync.

## Защита runtime

Контентная синхронизация не должна стирать состояние партии.

При несовместимости нужна явная scoped migration.

## Переименования и удаления

Стабильный ID — главный идентификатор.

Переименование файла при неизменном ID не создаёт новую сущность.

Удаление SOURCE требует обновления только затронутых generated-ссылок и проверки dangling IDs.

## Бинарные файлы

Изображения, PDF, аудио и видео:
- сначала сравниваются по hash/SHA;
- передаются только если изменились;
- metadata-only изменение не требует повторной передачи бинарника.

## Конфликты

### SOURCE conflict
Один канонический файл изменён независимо в разных source-ветках/копиях.

Автоматически не перезаписывать.

### Generated drift
Generated-файл изменён вручную в приложении.

Не импортировать в канон. Регенерировать либо перенести одобренное изменение в SOURCE.

### Runtime incompatibility
Новая версия generated-данных несовместима со старым сохранением.

Решается runtime migration.

### Schema mismatch
Exporter и приложение ожидают разные схемы.

Публикацию остановить до явного решения.

## Атомарная публикация

Порядок:
1. сгенерировать затронутые выходы;
2. проверить;
3. проверить связи;
4. перенести изменённые assets;
5. опубликовать generated-файлы;
6. обновить sync manifest последним.

Если проверка не прошла, baseline не продвигается.

## Sync manifest

Минимум:

```yaml
source_repository: bestkvestnn-pixel/dimnadvod
source_revision: <commit SHA>
export_schema_version: <version>
sync_status: success
```

Позже можно добавить:
- target revision;
- exporter version;
- hashes;
- changed paths;
- migration version;
- timestamp;
- conflict/error status.

Manifest — служебное состояние синхронизации, не канон.

## Минимальная запись

Если результат регенерации идентичен текущему файлу:
- не переписывать;
- не создавать commit;
- не отмечать как изменение.

## Когда допустим полный rebuild

- первая сборка;
- глобальная смена export schema;
- потерян/повреждён dependency index;
- неизвестен baseline;
- глобально изменился exporter;
- область влияния нельзя безопасно определить;
- пользователь явно потребовал полный rebuild/audit.

## Тестовые данные

Fixtures и прототипы приложения должны быть отделены от production generated data и явно помечены как test-only.

## Успешное завершение

Синхронизация завершена только когда:
1. определена дельта;
2. новые инструкции прочитаны первыми;
3. прочитаны затронутые SOURCE;
4. разрешены нужные зависимости;
5. пересобраны только затронутые outputs;
6. ссылки валидны;
7. assets присутствуют;
8. runtime не повреждён;
9. manifest указывает точную source revision;
10. baseline обновлён после успешной проверки.

> **Один авторский источник. Много производных представлений. Runtime остаётся runtime.**
